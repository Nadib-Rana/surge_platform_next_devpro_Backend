# API Response Style Guide

This guide describes the response contract used by the Surge Platform API and how to reproduce it in another NestJS project.

## 1. Standard response contracts

Every successful HTTP response uses this envelope:

```json
{
  "success": true,
  "statusCode": 200,
  "message": "User fetched successfully",
  "requestId": "d63b58ce-e521-42d7-b007-b634c6ef51aa",
  "timestamp": "2026-07-20T08:30:00.000Z",
  "path": "/users/123",
  "data": {
    "id": "123",
    "name": "Example User"
  }
}
```

Every failed HTTP response uses this envelope:

```json
{
  "success": false,
  "statusCode": 404,
  "message": "User not found",
  "requestId": "d63b58ce-e521-42d7-b007-b634c6ef51aa",
  "timestamp": "2026-07-20T08:30:00.000Z",
  "path": "/users/123",
  "errors": [
    {
      "code": "NOT_FOUND",
      "message": "User not found"
    }
  ]
}
```

Rules:

- `success` must agree with the HTTP status.
- `statusCode` must be the real HTTP response status, not always `200` or `400`.
- `message` is a short, human-readable summary.
- `requestId` correlates responses and server logs.
- `timestamp` is generated by the server in ISO 8601 UTC format.
- `path` is the requested API path.
- Success responses contain `data`; error responses contain `errors`.
- Do not return both `data` and `errors` in the same response.
- Optional properties must be omitted when they have no value.

## 2. Paginated response

List endpoints put the array in `data` and pagination information in `meta`:

```json
{
  "success": true,
  "statusCode": 200,
  "message": "Users fetched successfully",
  "requestId": "d63b58ce-e521-42d7-b007-b634c6ef51aa",
  "timestamp": "2026-07-20T08:30:00.000Z",
  "path": "/users?page=2&limit=10",
  "data": [],
  "meta": {
    "page": 2,
    "limit": 10,
    "total": 35,
    "totalPages": 4,
    "hasNext": true,
    "hasPrevious": true
  }
}
```

Services should return a `PaginatedResponseDto` (or an equivalent tagged object). The global success interceptor moves its `data` and `meta` into the response envelope.

## 3. Error details

Each item in `errors` follows this shape:

```ts
interface ErrorDetail {
  code: string;
  message: string;
  field?: string;
}
```

Use stable, uppercase application codes such as:

- `VALIDATION_ERROR`
- `AUTHENTICATION_ERROR`
- `AUTHORIZATION_ERROR`
- `NOT_FOUND`
- `CONFLICT_ERROR`
- `RATE_LIMIT_ERROR`
- `INTERNAL_ERROR`
- `EXTERNAL_SERVICE_ERROR`
- `DB_P2002`

Clients should make decisions from `statusCode` and `errors[].code`, not by comparing message text.

A validation failure should look like this:

```json
{
  "success": false,
  "statusCode": 400,
  "message": "Validation failed",
  "requestId": "d63b58ce-e521-42d7-b007-b634c6ef51aa",
  "timestamp": "2026-07-20T08:30:00.000Z",
  "path": "/users",
  "errors": [
    {
      "code": "VALIDATION_ERROR",
      "message": "email must be an email",
      "field": "email"
    }
  ]
}
```

## 4. NestJS building blocks

Copy or recreate these parts in the target project:

1. `ApiResponseDto<T>` and `ApiErrorResponseDto` define the public contract.
2. `PaginationMetaDto` and `PaginatedResponseDto<T>` define paginated service results.
3. `ResponseStandardizationInterceptor` wraps every successful controller result.
4. `AllExceptionsFilter` converts all thrown exceptions into the error contract.
5. `BaseException` and its HTTP-specific subclasses provide stable error codes.
6. `ResponseMessage` lets a route declare its success message.
7. `RequestIdMiddleware`, `AsyncLocalStorage`, and `ContextService` propagate a request ID.
8. A global `ValidationPipe` validates and transforms incoming DTOs.

Reference implementations in this project:

- `src/common/dto/api-response.dto.ts`
- `src/common/dto/api-error-response.dto.ts`
- `src/common/dto/pagination.dto.ts`
- `src/common/interceptors/response-standardization.interceptor.ts`
- `src/common/filters/all-exceptions.filter.ts`
- `src/common/exceptions/base.exception.ts`
- `src/common/exceptions/http.exceptions.ts`
- `src/common/decorators/response-message.decorator.ts`
- `src/common/middleware/request-id.middleware.ts`
- `src/common/context/`

## 5. Global registration

Register the response interceptor as an application interceptor:

```ts
providers: [
  {
    provide: APP_INTERCEPTOR,
    useClass: ResponseStandardizationInterceptor,
  },
]
```

Apply request-ID middleware to all routes:

```ts
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer.apply(RequestIdMiddleware).forRoutes("*");
  }
}
```

Register validation and the exception filter during bootstrap:

```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    forbidNonWhitelisted: true,
  }),
);

const httpAdapterHost = app.get(HttpAdapterHost);
const contextService = app.get(ContextService);
app.useGlobalFilters(
  new AllExceptionsFilter(httpAdapterHost, contextService),
);
```

The middleware must run before controllers, the interceptor wraps successful results, and the filter owns all failed results.

## 6. Controller and service rules

Controllers return raw domain data. They must not manually construct the outer response envelope:

```ts
@Post()
@ResponseMessage("User created successfully")
create(@Body() dto: CreateUserDto) {
  return this.usersService.create(dto);
}
```

Use NestJS status decorators when the default is not correct:

```ts
@Delete(":id")
@HttpCode(HttpStatus.NO_CONTENT)
remove(@Param("id") id: string) {
  return this.usersService.remove(id);
}
```

Services return data or throw exceptions:

```ts
const user = await this.prisma.user.findUnique({ where: { id } });

if (!user) {
  throw new NotFoundException("User");
}

return user;
```

For pagination:

```ts
return new PaginatedResponseDto(users, total, page, limit);
```

Do not return `{ success: false }` from a service for an HTTP failure. Throw a typed exception so the HTTP status and response body remain consistent.

## 7. HTTP status conventions

Use standard status semantics:

| Operation | Status |
| --- | ---: |
| Successful read/update | `200` |
| Successful creation | `201` |
| Successful deletion with no body | `204` |
| Invalid input | `400` |
| Missing/invalid authentication | `401` |
| Authenticated but not permitted | `403` |
| Resource not found | `404` |
| Duplicate/state conflict | `409` |
| Payload too large | `413` |
| Rate limited | `429` |
| Unexpected server failure | `500` |
| Upstream service failure | `502` |
| Upstream timeout | `504` |

For `204 No Content`, do not send a JSON envelope because HTTP 204 responses cannot contain a body. Use `200` if the client needs a response message or deleted resource.

## 8. Security and production behavior

- Include stack traces only outside production.
- Never expose database queries, credentials, tokens, raw upstream responses, or internal exception objects.
- Log full internal errors on the server with the same `requestId` returned to the client.
- Convert database errors into safe application messages and stable codes.
- Accept an incoming `x-request-id` only if it meets your trust and format rules; otherwise generate a UUID.

Optional error properties such as `instruction`, `details`, and `isVerified` should be used only when they are part of a documented client workflow. Avoid making the general error contract domain-specific.

## 9. Improvements to make when copying this project

The current project is a useful reference, but the target project should address these details:

1. Its validation `exceptionFactory` converts validation errors to strings, while the exception filter is written to traverse structured validation errors. Either remove the custom factory and let NestJS return its standard message array, or define one shared validation-error format and make the filter consume it directly.
2. `ApiResponseDto` assigns `meta = undefined`, which can be serialized differently depending on the HTTP adapter/serializer. Explicitly omit optional properties when absent and add contract tests for the exact JSON output.
3. Reading response-message metadata only from the handler prevents controller-level defaults. Use `reflector.getAllAndOverride(RESPONSE_MESSAGE_KEY, [context.getHandler(), context.getClass()])` if controller-level messages are desired.
4. Decide whether `path` includes the query string. The current `request.url` does; use `request.path` if the public contract should contain only the route path.
5. Do not wrap file streams, redirects, Server-Sent Events, or already-standardized responses. Add interceptor opt-out metadata for those routes.

## 10. Acceptance checklist

Before adopting the style, verify that:

- All ordinary success responses use the same envelope.
- All application, validation, database, and unknown errors use the error envelope.
- Actual HTTP status and body `statusCode` always match.
- Every response and corresponding log entry share a request ID.
- Pagination metadata is correct for empty and final pages.
- Stack traces never appear in production.
- Swagger documents the envelope rather than only the inner DTO.
- Contract tests cover `200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`, and `500` cases.
- Streaming, download, redirect, and health-check endpoints have an explicit wrapping policy.
